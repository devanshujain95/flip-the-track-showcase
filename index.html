04

Describe your approach to testing and improving QA

I approach QA as something that starts during the build, not only at the end. For this kind of app, I would test the game flow, permissions, camera/audio capture, backend behavior, and production observability before widening access.

  • I’d write unit test cases with Jest for scoring helpers, room state transitions, countdown logic, API payload validation, and edge cases around reconnects or missing media.
  • I’d test permissions deliberately on iOS and Android, including first install, denied camera or microphone access, permission recovery, and the exact copy shown when access is needed.
  • I’d run integration checks for the highest-risk mobile flows: room join, Declare War countdown, camera capture, audio playback, upload retry, AI score request, and result reveal.
  • On the backend, I’d use the Firebase Functions logger with Google Cloud Logging for structured request IDs, AI scoring failures, upload errors, retries, and latency signals.
  • For crash visibility, I’d wire Firebase Crashlytics into release builds, track non-fatal errors around camera, upload, and AI verdict flows, and review crash-free sessions before widening test groups.
  • I’d use Firebase Performance Monitoring where it helps for startup, network latency, and screen traces, especially around capture, upload, and score reveal moments.
  • I’d run TestFlight, Google Play internal testing, and Firebase App Distribution builds with a repeatable smoke checklist before store submission.

How my experience maps to this app

A clearer map of the main project needs, the relevant proof, and the technical path I would use for Flip the Track.

01

Shipped React Native, Expo, and native-module mobile work

I’ve shipped multiple applications on Google Play and the Apple App Store. From building apps in Expo and React Native to implementing native modules like Vision Camera, I have detailed, hands-on experience managing this kind of cross-platform mobile application from product flow to store-ready release.

02

Realtime room sync for two players

Firebase Realtime Database should be the shared source of truth for each room: players, phase, server timestamp, countdown deadline, uploads, and result state. Clients subscribe to that state, while transactions and Cloud Functions for Firebase handle sensitive transitions so both devices converge to the same phase after reconnects, slow networks, or duplicate taps.

03

Fair Declare War countdown

The countdown should not depend on each phone’s local timer. The backend writes a start time, deadline, and room phase version; each app displays the remaining time from the server-backed timestamp and ignores stale state changes.

04

Secure AI scoring and commentary

AI calls should stay server-side, with API keys never exposed to the app. The backend validates uploads, sends controlled scoring inputs to the model, handles retries, logs failures, and writes a normalized verdict back to the room state.

05

Camera, upload, and interaction polish

Vision Camera covers recording and permission states, upload retries protect against unreliable networks, and Reanimated plus Lottie can make the battle flow feel responsive without blocking the main interaction path.

06

Product layer and release readiness

Profiles, match history, leaderboard aggregation, CI/CD, TestFlight, Google Play internal testing, app store assets, and release candidate checks should be treated as part of the product build, not an afterthought.

Milestone plan

I’m estimating this as a maximum 8-week build to take the full product from scratch through App Store and Google Play release.

  1. Foundation, auth, navigation, and battle-room base Set up the Expo SDK 56 project structure, React Navigation auth/app stacks, permissions layer, Zustand state, MMKV persistence, light/dark theming, icons, SVGs, fonts, and app styling. Integrate Firebase Auth, Firebase Realtime Database, Cloud Functions for Firebase, and the realtime battle-room state models. Add unit test cases for navigation, auth guard, room state transitions.
  2. Camera intelligence, liveness, audio, and upload pipeline Implement Vision Camera capture with Apple Vision and MediaPipe signals for liveness: eye blink detection, subtle face movement, face capture quality, gaze cues, face angle, and facing direction. Add audio playback, lip-sync timing, lyrics sync, media permissions, and the upload pipeline. Add unit test cases for permission-state coverage, upload retry tests, and integration checks for capture-to-upload flow.
  3. AI verdict system Build Gemini video scoring, Claude commentary, Cloud Functions security, retry handling, structured logs, normalized verdict storage, and score reveal UX. Add backend unit test cases for scoring payload validation, retry/failure-path tests, Cloud Logging review, and frontend integration checks for pending, success, and error reveal states.
  4. Competition layer and product polish Add match history, leaderboard aggregation, user profiles, moderation basics, analytics events, empty/error states, and final interaction polish.
  5. Store submission and release hardening Prepare app icons, screenshots, privacy details, Firebase Crashlytics, release builds, TestFlight, Google Play internal testing, App Store submission, and Google Play submission. Tests: release-candidate smoke tests, permission copy review, crash-free session review, backend log review, store metadata checklist, and final iOS/Android device QA.
